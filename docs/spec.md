# シンプルTodoアプリ 仕様書

Nov 17, 2026 · @Erika ・ 最終更新 2026-11-19(MVP 完成)

**この文書(リポジトリの `docs/spec.md`)が正。** 最初の版は claude.ai のドキュメントにもあるが、そちらは更新しない。機能を変えたら、ここを直す。

## 1. 概要

自分のタスクを「追加 → 確認 → 完了」できる、1人用のWeb Todoアプリを作る。まずは最小限(MVP)を2〜3週間で動かし、使いながら機能を足す。

| 項目 | 内容 |
| --- | --- |
| 目的 | やることを1か所にまとめ、期限と優先度で迷わず次の作業を選べるようにする |
| 対象ユーザー | 自分(個人利用)。将来は他の人も登録できる作り |
| 使う場所 | PCとスマホのブラウザ(レスポンシブ) |
| MVPでできること | ログイン、タスクの追加・編集・完了・削除、リスト分け、期限・優先度、絞り込み |
| MVPでやらないこと | チーム共有、通知、繰り返しタスク、ファイル添付 |

**用語**: タスク = やること1件。リスト = タスクを入れるフォルダ(例:仕事、買い物)。どのリストにも入れないタスクは「インボックス」に入る。

## 2. 決めたこと(不明点へのおすすめ)

迷いそうな点は、「小さく作って後で広げやすい」を基準に決めた。違う希望があればこの表だけ直せばよい。

| 論点 | おすすめ | 理由 |
| --- | --- | --- |
| 作るもの | Webアプリ(スマホ対応) | アプリストア申請が不要。URLだけでどの端末でも使える |
| 技術 | Next.js 16(App Router)+ React 19、Prisma 7(`@prisma/adapter-pg` で接続)、Supabase(PostgreSQL・認証。`@supabase/ssr`)、Zod 4 | PortoGenで使った構成なので学習コストが低い。無料枠で運用できる。Next.js 16 では Middleware の名前が変わり、`src/proxy.ts`(Proxy)になった |
| 公開先 | Vercel | Next.jsと相性がよく、GitHubにpushするだけで自動デプロイ。サーバーの処理は Vercel のソウル(icn1)、DB は Supabase のソウル(ap-northeast-2)で動かす(近い場所にそろえて速くするため) |
| ログイン | あり(メール+パスワード) | PCとスマホで同じデータを見るには「誰のデータか」の区別が必要。Supabase Authで実装が軽い |
| 新規登録 | 誰でも登録できる。確認メールは送らない(Supabase の Confirm email はオフ) | 登録してすぐ使えるようにするため |
| タスクの分類 | リスト(1タスクに1つ)。タグは後回し | タグは多対多の中間テーブルが必要で複雑。まずはフォルダ式で十分 |
| リストの色 | 8色(青・緑・オレンジ・紫・赤・水色・ピンク・茶色)から、まだ使っていない色を自動で付ける。「…」メニューから変えられる | 作るときに迷わず、あとから見分けやすくできる |
| 状態 | 未完了 / 完了の2つ | 「進行中」を入れるとかんばん寄りになる。Todoはチェックできればよい |
| 優先度 | 高・中・低の3段階(初期値=中) | 5段階だと選ぶのに迷う |
| 期限 | 日付のみ(時刻なし)、任意 | 時刻まで持つとタイムゾーン処理が必要になる |
| 「今日」の判定 | 利用者の端末の日付で行う。API では画面から `&today=YYYY-MM-DD` で渡す | サーバーの時計は UTC のため(第8章 ルール5) |
| 削除 | 確認ダイアログを出して完全削除 | 個人用なので「ごみ箱」機能は不要。完了で残す運用で代用 |
| リストを消したら | 中のタスクはインボックスへ移動 | リストを消しただけでタスクが消える事故を防ぐ |
| 並び順(初期) | 未完了が上 → 期限が近い順 → 優先度が高い順 | 「今やるべきもの」が一番上に来る |

## 4. ユーザーフロー

アプリを開くとまずログインを確かめ、その後はほぼすべての操作を「タスク一覧」の中で行う。

&#91;embedded content: 画面遷移と一覧での操作\]

**「タスクを追加して片付ける」一歩ずつの例**

1. ログインすると S-03 が開き、左の「今日」が選ばれている。
2. 「仕事」リストを押し、上の入力欄に「請求書を送る」と打ってEnter → 一覧に1行増える(裏で POST /api/tasks)。
3. その行を押すと右に S-04 が開く。期限を「明日」、優先度を「高」にする → 自動保存(PATCH)。
4. ×で閉じる。翌日「今日」を開くとこのタスクが出ている。
5. 終わったらチェック → 取り消し線が入り、「未完了」タブからは消える(status=done)。

## 5. 画面仕様

画面は4つだけ。メインは「タスク一覧」で、編集はページ移動せず右側のパネル(スマホでは全画面)で行う。移動が少ないほど操作が速いから。

| 画面 | URL | 主な要素 | 動き |
| --- | --- | --- | --- |
| トップ | / | (なし) | ログインしていれば /tasks へ、していなければ /login へ振り分ける |
| S-01 ログイン | /login | メール、パスワード、ログインボタン、新規登録へのリンク。「パスワードを忘れた方」のリンクは置かない | 成功 → S-03。失敗 → 「メールアドレスまたはパスワードが違います」 |
| S-02 新規登録 | /signup | 名前(1〜50文字)、メール、パスワード、登録ボタン。パスワード欄の下に「あと○文字(8文字以上)」 | 成功 → 自動ログインしてS-03 |
| S-03 タスク一覧 | /tasks?view=today(/tasks だけでも「今日」)、/tasks?view=inbox、/tasks?list=<リストのID>。絞り込みタブは &status=todo または &status=done(付けなければ「すべて」) | 左: サイドバー(今日、インボックス、リスト一覧、＋リスト)。中央: 追加入力欄、絞り込みタブ、タスク行 | 行のチェックで完了。行をクリックでS-04を開く |
| S-04 タスク詳細 | /tasks/<タスクのID>(開く前のビューの ? 以降を引き継ぐ。例: /tasks/<ID>?view=today) | タイトル、メモ、期限、優先度、リスト選択、削除ボタン | 入力欄から離れたら自動保存。×で閉じてS-03へ |
| メニュー | (S-03内) | ユーザー名、ログアウト | ログアウト → S-01 |

**タスク行の見た目**: \[☐\] タイトル · 期限(期限切れは赤) · 優先度マーク(高のみ) · リスト名(「今日」ビューのみ) · 「メモあり」の印。完了した行は取り消し線で薄くする。期限は「今日 / 明日 / 昨日 / 11/22」の形で出す。優先度「高」の旗は、完了したタスクにも残す。

**空のとき**: タスク0件なら「タスクはありません。入力欄から追加しましょう」と表示する。「完了」タブで0件のときは「完了したタスクはまだありません」と表示する。

**ログインしていない人が /tasks を開いたら**: /login に自動で戻す(他人のデータを見せないため)。

### タスク一覧(S-03)の動き

- **ビューの切り替え**: ページを読み直さず、URL だけを変える。再読み込みやブラウザの「戻る」で同じビューに戻れる。絞り込みタブの切り替えは「戻る」の履歴に積まない。
- **初期表示**: ログイン後は「今日」ビュー、絞り込みタブは「すべて」。
- **「今日」ビュー**: 見出しに日付(例: 11月19日(木))。区切りは「期限切れ / 今日 / 完了」で、「完了」には今日完了にしたタスクを出す。進み具合「○件中○件完了」を出す。各行にリスト名(どのリストにも入っていなければ「インボックス」)を出す。「今日」の区切りの中では、期限の「今日」の文字は省く。
- **インボックス・各リスト**: 区切りは「未完了 / 完了」。進み具合「○件中○件完了」を出す。
- **「完了」の区切り**: 「すべて」タブのときは、見出しを押すと畳める。
- **追加欄の案内文**: 「今日やることを追加」「インボックスに追加」「『仕事』に追加」と、開いているビューに合わせる。
- **リストの URL**: 消したリスト・他人のリストの URL を開いたときは「今日」を出す。開いているリストを消したら、インボックスを開く。

### サイドバー

- 「今日」(期限が今日以前の未完了タスクの数)、「インボックス」(未完了の数)、リスト(色・名前・未完了の数)、「リストを追加」。今いるビューに印を付ける。
- **リストの追加**: 「リストを追加」を押し、名前を入れて Enter。Esc でやめる。保存を待ってから(「作成中…」と出す)、そのリストを開く。
- **各リストの「…」メニュー**: 「名前を変更」/ 色(8色)/「削除」。PC ではマウスを乗せたとき・フォーカスしたときに「…」を出し、スマホでは常に出す。名前の変更は Enter で保存、Esc でやめる(保存中は「保存中…」)。
- 下に、ユーザー名・メールアドレスと「ログアウト」。

### タスク詳細(S-04)

- **保存のしかた**: タイトルとメモは、入力欄から離れたら自動保存する(タイトルは Enter でも)。期限・優先度・完了・リストは、押したらすぐ保存する。保存できたら「保存しました」と出す。
- **期限**: 日付の入力欄と「今日 / 明日 / なし」のボタン。下に「11/16(月)」の形で出し、期限切れなら「・期限切れ」を赤字で付ける。
- **メモ**: 「○ / 1000」の文字数を出す。空にすると「メモなし」として保存する(「メモあり」の印も消える)。
- **リスト**: 「インボックス」と各リストから選ぶ。
- **閉じ方**: ×、Esc キー、ブラウザの「戻る」。スマホでは左上の「‹ 今日」など(元のビューの名前)。
- PC ではパネルの上部に、入っているリストの名前を出す。下に「○/○ 作成」。

## 6. ERD・データ設計

データを保存する箱(テーブル)は users / lists / tasks の3つだけ。矢印は「1件に対して複数件がぶら下がる」関係を表す。

&#91;embedded content: ERD · 3テーブル\]

| テーブル | 役割 | 設計のポイント |
| --- | --- | --- |
| users | ログインする人 | idはSupabase Authが発行するIDをそのまま使う。パスワードはAuth側が暗号化して持つのでこの表には置かない |
| lists | タスクを入れるフォルダ | (user\_id, name) の組み合わせで一意にし、同名リストを防ぐ |
| tasks | やること1件 | list\_idが空 = インボックス。リスト削除時は ON DELETE SET NULL で空に戻し、タスクを残す |

**列の一覧**(すべて snake\_case。id は uuid)

users

| 列 | 型 | 空可 | 初期値 | 説明 |
| --- | --- | --- | --- | --- |
| id | uuid | | | Supabase Auth の auth.users の id。auth.users を参照し、Auth のユーザーを消すと一緒に消える |
| email | text | | | 一意 |
| name | varchar(50) | | | 表示名 |
| created\_at | timestamptz | | 現在時刻 | |
| updated\_at | timestamptz | | 現在時刻 | 更新のたびに変わる |

lists

| 列 | 型 | 空可 | 初期値 | 説明 |
| --- | --- | --- | --- | --- |
| id | uuid | | 自動 | |
| user\_id | uuid | | | users を参照(ユーザーを消すと一緒に消える) |
| name | varchar(30) | | | (user\_id, name) で一意 |
| color | varchar(7) | 可 | | "#3B5BDB" の形。8色のどれか |
| created\_at | timestamptz | | 現在時刻 | サイドバーはこの順に並べる |
| updated\_at | timestamptz | | 現在時刻 | |

tasks

| 列 | 型 | 空可 | 初期値 | 説明 |
| --- | --- | --- | --- | --- |
| id | uuid | | 自動 | |
| user\_id | uuid | | | users を参照(ユーザーを消すと一緒に消える) |
| list\_id | uuid | 可 | | lists を参照。空 = インボックス。リストを消すと空に戻る(SET NULL) |
| title | varchar(100) | | | |
| description | varchar(1000) | 可 | | メモ |
| due\_date | date | 可 | | 期限(時刻なし) |
| priority | high / medium / low | | medium | 優先度 |
| status | todo / done | | todo | 状態 |
| completed\_at | timestamptz | 可 | | 完了にした日時 |
| created\_at | timestamptz | | 現在時刻 | |
| updated\_at | timestamptz | | 現在時刻 | |

**users の作り方**: Supabase Auth に登録すると、DB のトリガーが users に1行を自動で作る。名前が無いときはメールアドレスの @ より前を使う。データが欠けていても登録自体は失敗させない。

**なぜ tasks にも user\_id を持つか**: リスト経由で持ち主をたどると、インボックス(list\_idが空)のタスクは誰のものかわからなくなる。また、API で「user\_id = 自分」という単純な条件で絞れる(RLS の予備の守りも同じ条件で書ける。第9章)。

**空可の意味**: 入力しなくてもよい項目(NULLを許可)。それ以外は必須。statusの初期値は todo、priority の初期値は medium。

**検索を速くする索引(インデックス)**: tasks の (user\_id, status, due\_date)。一覧と「今日」ビューがこの3つで絞って並べるから。

## 7. API仕様

画面は下の9本のAPIでデータを読み書きする。どのAPIもログイン必須で、自分のデータ以外は返さない。ログイン・登録はSupabase Authが持つ仕組みを使うので自作しない。

| メソッド | パス | やること | 使う画面 |
| --- | --- | --- | --- |
| GET | /api/tasks | 一覧取得。`?listId=` `?view=today` `?status=todo\|done` で絞る | S-03 |
| POST | /api/tasks | 新規作成(title必須) | S-03 |
| GET | /api/tasks/:id | 1件取得 | S-04 |
| PATCH | /api/tasks/:id | 一部更新(完了切替もこれ: `{"status":"done"}`) | S-03, S-04 |
| DELETE | /api/tasks/:id | 削除 | S-04 |
| GET | /api/lists | リスト一覧(各リストの未完了数付き) | S-03 |
| POST | /api/lists | リスト作成 | S-03 |
| PATCH | /api/lists/:id | 名前・色の変更 | S-03 |
| DELETE | /api/lists/:id | 削除(中のタスクはインボックスへ) | S-03 |

**例: タスクを追加するときのやりとり**

```json
→ POST /api/tasks
{ "title": "請求書を送る", "listId": "…", "dueDate": "2026-11-20" }

← 201 Created
{ "id": "…", "title": "請求書を送る", "description": null, "status": "todo", "priority": "medium", "dueDate": "2026-11-20", "completedAt": null, "createdAt": "…", "listId": "…" }
```

**各 API の細かい決まり**

- **GET /api/tasks の絞り込み**:
  - `?listId=<リストのID>` でそのリスト、`?listId=inbox` でインボックス。
  - `?view=today&today=YYYY-MM-DD` で、期限が today 以前の未完了タスク(全リスト横断)。today には画面が端末の今日の日付を入れる。today が無いと 400。
  - `?status=todo` または `?status=done`。
  - 組み合わせてもよい。知らない項目や正しくない値は 400、他人のリスト・存在しないリストは 404。
  - 画面は最初に全部のタスクを読み込み、ビューの切り替えは画面の中で絞る(切り替えのたびに通信しないため)。
- **POST /api/tasks**: `title`(必須)、`listId`(無ければインボックス)、`dueDate` を受け付ける。優先度は作成後に PATCH で変える。他人のリストを指定したら 404。
- **PATCH /api/tasks/:id**: 変えられる項目は title / description / dueDate / priority / status / listId。送った項目だけを変える。何も送らない・知らない項目は 400(「変更する項目を指定してください」「リクエストの形式が正しくありません」)。移す先が他人のリストなら 404「リストが見つかりません」。
- **リスト**: 返す形は `{ "id", "name", "color", "todoCount" }`。名前の重複は 400「同じ名前のリストがあります」。色は決まった8色のどれか(それ以外は 400)。作るときの色は自動。
- **成功時の番号**: 作成は 201、削除は 204(本文なし)、それ以外は 200。

**エラー時の返し方**: 入力ミス = 400、未ログイン = 401(「ログインしてください」)、他人のデータや存在しないID = 404(「タスクが見つかりません」「リストが見つかりません」)。本文は `{ "error": "メッセージ" }` に統一。他人のデータに403ではなく404を返すのは、「そのIDが存在すること」自体を教えないため。

補足: Next.jsではこれを Route Handler(`app/api/.../route.ts`)か Server Actions で作れる。仕組みを理解しやすいのはRoute Handlerなので、まずはそちらをおすすめする。(実装は Route Handler で作った。ログイン・登録・ログアウトだけは Server Actions。)

## 8. 状態遷移・業務ルール・バリデーション

タスクの状態は「未完了(todo)」と「完了(done)」の2つだけで、チェックで何度でも行き来できる。

| 操作 | 前の状態 | 後の状態 | 裏で起きること |
| --- | --- | --- | --- |
| 追加 | (なし) | todo | created\_atを記録 |
| チェックを入れる | todo | done | completed\_atに現在時刻を入れる |
| チェックを外す | done | todo | completed\_atを空に戻す |
| 削除 | todo / done | (なし) | 行ごと消える。元に戻せない |

**業務ルール**

1. ユーザーは自分のタスクとリストしか見れないし変えられない。
2. リストを指定しないタスクはインボックス(list\_idが空)に入る。
3. リストを削除すると、中のタスクはインボックスへ移る(確認ダイアログで「○件のタスクはインボックスへ移ります」と伝える)。
4. 「期限切れ」= 未完了で、期限が今日より前。完了したタスクは期限が過ぎていても赤くしない。
5. 「今日」の判定はユーザーの端末の日付(あなたならWITA)で行う。サーバーのUTCで判定すると朝8時まで日付がずれるため。API では画面から `&today=YYYY-MM-DD` で渡す。
6. 同じユーザー内でリスト名の重複は不可(サイドバーで区別がつかなくなるため)。前後の空白を削除してから比べ、大文字・小文字は区別する(「Work」と「work」は別の名前)。タスク名の重複は可。
7. 「今日」ビューに出すのは、期限が今日以前の未完了タスクと、今日(端末の日付で)完了にしたタスク。

**入力チェック(バリデーション)**

| 項目 | ルール | エラー表示 |
| --- | --- | --- |
| タスクのタイトル | 必須、1〜100文字、前後の空白は削除 | 「タイトルを入力してください」「100文字以内で入力してください」 |
| メモ | 任意、1,000文字まで | 「1,000文字以内で入力してください」 |
| 期限 | 任意、日付形式。過去の日付も可 | 「正しい日付を選んでください」 |
| 優先度 | high / medium / low のどれか | (選択式なので出ない。API では「優先度は high / medium / low のどれかを指定してください」) |
| リスト名 | 必須、1〜30文字、前後の空白は削除、重複不可 | 「リスト名を入力してください」「30文字以内で入力してください」「同じ名前のリストがあります」 |
| 名前 | 必須、1〜50文字 | 「名前を入力してください」「50文字以内で入力してください」 |
| メール | 必須、メール形式 | 「メールアドレスを入力してください」「メールアドレスの形式が正しくありません」。登録済みなら「このメールアドレスはすでに登録されています」 |
| パスワード | 8文字以上 | 「8文字以上で入力してください」 |

チェックは画面側とAPI側の両方で行う。画面側はすぐ教えるため、API側は画面を経由しない不正なデータを止めるため(同じルールをZodで1か所に書いて使い回すと楽)。

## 9. 非機能要件と開発ステップ

「動くこと」以外に守る条件は次の5つ。

| 分類 | 要件 |
| --- | --- |
| セキュリティ | 本当の守りは API。どの API も、ログイン中のユーザーの user\_id で必ず絞り込み、他人のデータは 404 を返す。ログインの確認は、サーバーで署名を検証する `getClaims()` で行う。Prisma は DB に管理者として接続するので、Supabase の RLS(行単位のアクセス制限)は Prisma には効かない。RLS は全テーブルで有効にし、「user\_id が自分の行だけ」のポリシーを付けてある。これは Supabase の Data API(supabase-js から直接 DB を読む道)に対する予備の守り |
| 速さ | チェックや追加は画面を先に変え、後から保存する(楽観的更新)。失敗したら元に戻してエラー表示 |
| 表示 | 横幅375px(スマホ)〜1440px(PC)で崩れない。768px未満ではサイドバーをメニューボタンにたたむ。詳細パネルの出し方は画面幅で変える(第5章)。スマホで押せる範囲は 44px 以上 |
| 対応ブラウザ | Chrome、Safari、Edgeの最新版 |
| 運用コスト | VercelとSupabaseの無料プランの範囲で運用する |

**開発ステップ(この順に進めると、毎回「動く状態」を保てる)** ― すべて完了(2026-11-19)

1. 環境づくり: Next.jsプロジェクト作成、Supabaseプロジェクト作成、Git の準備 ― 完了

4. タスクの基本: 追加・一覧・完了切替(F-03〜F-05)。GitHub と Vercel をつないで公開し、スマホで試す ― 完了
5. 編集と削除: S-04パネル、期限、優先度(F-06〜F-09) ― 完了

**受入テストの例**: 別アカウントでログインし、最初のアカウントのタスクIDをURLに入れても404になること。リストを消しても中のタスクがインボックスに残ること。

**運用**

- **DB の変更**: マイグレーションは手元で行い、Supabase に反映してから push する(先に push すると、新しいコードが古い DB で動いてしまう)。手順は CLAUDE.md に書いてある。
- **DB への接続**: Supabase の Shared Pooler(IPv4)を使う。`db.<ref>.supabase.co` は IPv6 だけなので、手元の PC や Vercel からはつながらない。
- **Vercel の環境変数**: NEXT\_PUBLIC\_SUPABASE\_URL、NEXT\_PUBLIC\_SUPABASE\_PUBLISHABLE\_KEY、DATABASE\_URL の3つ。DIRECT\_URL(マイグレーション用)は Vercel に置かない。
- **新規登録**: 誰でも登録できるまま開けておく。
- **Supabase の無料プラン**: 使わない期間が続くと、プロジェクトが一時停止される。止まったらダッシュボードから再開する(止まっている間、ログインでは「通信できませんでした…」が出る)。
